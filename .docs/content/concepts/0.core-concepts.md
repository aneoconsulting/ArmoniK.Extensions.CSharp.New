# Core Concepts

## Blobs

In ArmoniK, data is managed through entities called "Results", which encompass all input and output data. To make this more intuitive, this SDK uses the term **blob** to describe any data entity flowing through a task graph — payloads, results, and data dependencies are all blobs.

A blob is described by:

- **Name** `string` — a user-defined name. If not provided, the SDK assigns a default.
- **ID** `string` — a unique identifier generated by ArmoniK; the SDK abstracts away its creation.
- **Content** `ReadOnlyMemory<byte>` — the actual data, uploadable to or downloadable from ArmoniK.
- **Session** `Session` — the session the blob belongs to.

Blobs are only ever created through the SDK — via `IBlobService`, obtained from `ArmoniKClient.BlobService`:

```csharp
var blob = await client.BlobService.CreateBlobAsync(session, "Payload", Encoding.ASCII.GetBytes("Hello"));
```

### Declaring blobs on a task graph: `BlobDefinition`

When building a `TaskDefinition` (see below), inputs and outputs are declared with `BlobDefinition`, which offers a factory per data source:

| Factory | Use for |
|---|---|
| `BlobDefinition.FromString(name, content, encoding?)` | Small string payloads |
| `BlobDefinition.FromByteArray(name, content)` | Raw byte payloads |
| `BlobDefinition.FromReadOnlyMemory(name, content)` | Byte payloads without an extra copy |
| `BlobDefinition.FromFile(name, filePath)` | Payloads read from disk |
| `BlobDefinition.FromBlobHandle(handle)` | Re-using a blob already created earlier (e.g. chaining a previous task's output as a new task's input) |
| `BlobDefinition.CreateOutput(name)` | Declaring an expected output, with no content yet — ArmoniK fills it in once the task completes |

Two fluent modifiers are also available:

- `.WithManualDeletion()` — opts the blob out of automatic cleanup.
- `.WithCallback(ICallback callback)` — registers a callback invoked once the blob's data is available:

  ```csharp
  ValueTask OnSuccessAsync(BlobHandle blob, byte[] rawData, CancellationToken cancellationToken);
  ValueTask OnErrorAsync(BlobHandle blob, Exception exception, CancellationToken cancellationToken);
  ```

  Callbacks are polled and invoked in the background by the `SessionHandle` you submitted the task through (see [Submitting Tasks](../user-guide/2.submitting-tasks.md)) — no need to poll blob status manually.

## TaskNodes

ArmoniK is a graph-oriented orchestrator: workflows are made of tasks with dependencies between them. This SDK represents each task as a **`TaskDefinition`**, a fluent builder:

- `.WithInput(name, BlobDefinition)` — a data dependency required before the task can run.
- `.WithOutput(name, BlobDefinition)` — an expected output, usually built with `BlobDefinition.CreateOutput(name)`.
- `.WithTaskOptions(TaskConfiguration)` — priority, max retries, partition, max duration, and any extra key/value `Options`.
- `.WithLibrary(DynamicLibrary)` — **only used for [dynamic workers](../user-guide/1.static-vs-dynamic-workers.md)**: associates the task with a specific uploaded worker library. Optional — a task destined for a static worker simply omits it.

`TaskDefinition` is a mutable builder: every `With*` call mutates the same instance and returns `this` (so you can chain calls in any order before submitting).

On the worker side, inputs and outputs declared on the `TaskDefinition` show up keyed by name on `ISdkTaskHandler.Inputs` / `ISdkTaskHandler.Outputs` — see [Static vs. Dynamic Workers](../user-guide/1.static-vs-dynamic-workers.md).

## Services

To keep responsibilities focused, the SDK exposes one service per concern, each reachable through `IQueryable`/async methods rather than one large client class:

- **`ISessionService`** — creates and manages the lifecycle of sessions (cancel, close, pause, resume, purge, delete).
- **`IBlobService`** — creates, uploads, downloads, lists, and queries blobs.
- **`ITasksService`** — submits tasks, lists and queries them, cancels them, and fetches detailed state.
- **`IEventsService`** — waits for blobs to become available (`WaitForBlobsAsync`).
- **`IHealthCheckService`** / **`IVersionsService`** / **`IPartitionsService`** — cluster health, version info, and partition metadata/queries.

## ArmoniKClient

`ArmoniKClient` is the entry point applications use to reach ArmoniK. It owns the gRPC channel pool and exposes every service as a property, plus session creation:

```csharp
var client = new ArmoniKClient(properties, loggerFactory);

IBlobService        blobs      = client.BlobService;
ITasksService        tasks      = client.TasksService;
ISessionService       sessions   = client.SessionService;
IEventsService        events     = client.EventsService;
IHealthCheckService   health     = client.HealthCheckService;
IVersionsService      versions   = client.VersionService;
IPartitionsService    partitions = client.PartitionsService;

SessionHandle session = await client.CreateSessionAsync(partitionIds: ["dllworker"],
                                                          taskOptions: defaultTaskOptions,
                                                          closeOnDispose: true);
```

`SessionHandle`, `TaskHandle`, and `BlobHandle` (returned by session creation, task submission, and blob creation respectively) wrap the underlying `SessionInfo`/`TaskInfos`/`BlobInfo` together with the `ArmoniKClient`, giving you convenience instance methods (e.g. `sessionHandle.CancelSessionAsync()`, `blobHandle.DownloadBlobDataAsync()`) instead of always going through the service objects directly.

See the [Reference](../reference/2.api-surface.md) for the full method signatures of every service and handle.
