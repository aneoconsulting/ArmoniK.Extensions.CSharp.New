# Submitting Tasks

## Submission is asynchronous and batched

`SessionHandle.Submit(...)` does not call the ArmoniK API synchronously:

```csharp
TaskHandle Submit(TaskDefinition task, CancellationToken cancellationToken = default);
ICollection<TaskHandle> Submit(ICollection<TaskDefinition> tasks, CancellationToken cancellationToken = default);
```

Instead, it pushes each `(TaskDefinition, TaskHandle)` pair onto an internal channel. A background loop batches pending tasks and submits them together once either threshold is reached:

- **`Properties.TaskSubmissionBatchSize`** — number of tasks per batch (default `1000`).
- **`Properties.TaskSubmissionBatchWindow`** — max time to wait before flushing a partial batch (default `5s`).

Each returned `TaskHandle` carries a `TaskCompletionSource<TaskInfos>` that only resolves once its batch has actually been submitted:

```csharp
var taskHandle = session.Submit(task);
var taskInfos  = await taskHandle.GetTaskInfosAsync(); // awaits submission if it hasn't happened yet
```

Both settings are configurable from your app configuration (see [Configuration](./4.configuration.md)) — tune `TaskSubmissionBatchSize`/`TaskSubmissionBatchWindow` up for high-throughput bulk submission, or down for lower per-task submission latency.

## Waiting for results

Two complementary ways to know when output data is ready:

### 1. Explicit wait via `IEventsService`

```csharp
await client.EventsService.WaitForBlobsAsync(session, [resultBlobInfo]);
var bytes = await client.BlobService.DownloadBlobAsync(resultBlobInfo);
```

Blocks (asynchronously) until every listed blob is available, then you download explicitly. Best when you have a small, known set of results to collect before continuing.

### 2. Callbacks via `ICallback`

Attach a callback to an output `BlobDefinition` when building the task:

```csharp
public class ResultCallback : ICallback
{
  public ValueTask OnSuccessAsync(BlobHandle blob, byte[] rawData, CancellationToken cancellationToken)
  {
    Console.WriteLine(Encoding.UTF8.GetString(rawData));
    return default;
  }

  public ValueTask OnErrorAsync(BlobHandle blob, Exception exception, CancellationToken cancellationToken)
  {
    Console.WriteLine($"Task failed: {exception.Message}");
    return default;
  }
}

var task = new TaskDefinition()
  .WithOutput("helloResult", BlobDefinition.CreateOutput("Result").WithCallback(new ResultCallback()))
  .WithTaskOptions(taskOptions);
```

Under the hood, `SessionHandle` runs a background poller (`CallbackRunner`) that periodically checks the status of every blob with a registered callback (interval controlled by `Properties.CallbackPollingInterval`, default `5s`), using the [LINQ query API](./3.querying-with-linq.md) to batch status lookups, and invokes `OnSuccessAsync`/`OnErrorAsync` once a blob completes or fails.

Prefer callbacks when you're submitting many tasks and want to react to each result as it lands, rather than waiting on all of them up front. You can also explicitly stop waiting on pending callbacks with `sessionHandle.CancelCallbacksAsync()`, or block until all of them have fired with `sessionHandle.WaitCallbacksAsync()`.

## Cleaning up a session

`SessionHandle` implements `IAsyncDisposable`/`IDisposable`. If created with `closeOnDispose: true`, disposing it closes the session automatically. You can also manage its lifecycle explicitly:

```csharp
await session.PauseSessionAsync();
await session.ResumeSessionAsync();
await session.StopSubmissionAsync();
await session.PurgeSessionAsync();  // delete task/result data, keep session metadata
await session.DeleteSessionAsync(); // delete the session entirely
```
