# Static vs. Dynamic Workers

Both approaches implement the same `IWorker` contract:

```csharp
public interface IWorker
{
  Task<TaskResult> ExecuteAsync(ISdkTaskHandler taskHandler, ILogger logger, CancellationToken cancellationToken);
  Task<HealthCheckResult> CheckHealth(CancellationToken cancellationToken = default);
}
```

The difference is entirely in **how and when your implementation ends up running inside the worker container**.

## Static workers

- Your `IWorker` implementation is compiled directly into a dedicated worker application (see [`StaticWorkerExample`](https://github.com/aneoconsulting/ArmoniK.Extensions.CSharp.New/tree/main/StaticWorkerExample)).
- `Program.cs` calls `ArmoniKWorker.Run<StaticServiceRequestContext<TWorker>>()`, which starts the gRPC worker server directly.
- `StaticServiceRequestContext<TWorker>` creates a **new `TWorker` instance for every task**, so your worker type needs a public parameterless constructor.
- You build and deploy your own Docker image (one image per worker implementation), and configure an ArmoniK partition to use it.
- The client submits a `TaskDefinition` **without** calling `.WithLibrary(...)`.

Use this when:
- You have a small, fixed set of task implementations.

## Dynamic workers

- Your `IWorker` implementation is a **plain class library** — no `Program.cs`, no gRPC hosting code (see [`DynamicWorkerExample`](https://github.com/aneoconsulting/ArmoniK.Extensions.CSharp.New/tree/main/DynamicWorkerExample)).
- You publish and zip it (`dotnet publish` + `ZipDirectory` MSBuild target), then upload the zip as a blob at submission time via `IBlobService.SendDllBlobAsync(...)`.
- A single, generic container image — [`ArmoniK.Extensions.CSharp.DynamicWorker`](https://github.com/aneoconsulting/ArmoniK.Extensions.CSharp.New/tree/main/ArmoniK.Extensions.CSharp.DynamicWorker), published as `dockerhubaneo/armonik-dynamic-dotnet-worker` — is deployed once to a partition and can run **any number of different implementations**.
- On the client, the task references the library with `DynamicLibrary { Symbol, LibraryPath }` and `.WithLibrary(dynamicLib)`; `Symbol` is the fully-qualified type name (e.g. `"DynamicWorkerExample.HelloWorker"`) and `LibraryPath` is the path to the assembly inside the extracted zip.

### How loading works under the hood

1. `DynamicServiceRequestContext` reads the `DynamicLibrary` info back out of the task's `TaskOptions` (it was stashed there as `LibraryPath`/`Symbol`/`LibraryBlobId` entries when the task was submitted).
2. `LibraryLoader` checks whether that `Symbol`+`LibraryBlobId` combination is already loaded for the current session; if so, it reuses the cached instance.
3. Otherwise, `WorkerService.CreateWorkerService(...)` pulls the zip bytes from the task's data dependencies, extracts them to disk, creates a **new, collectible `AssemblyLoadContext`**, loads the assembly, and instantiates your type via reflection.
4. When the session changes, all currently loaded worker services for the previous session are disposed and their `AssemblyLoadContext`s unloaded.

Use this when:
- Many different task implementations need to share the same deployed worker/partition.
- You want to add or update task implementations without rebuilding or redeploying the worker image.

## Summary

| | Static | Dynamic |
|---|---|---|
| Worker project type | Executable (`Program.cs` + `ArmoniKWorker.Run`) | Class library, no entry point |
| Deployment | One Docker image per implementation | One shared image (`armonik-dynamic-dotnet-worker`) for all implementations |
| Client task setup | `TaskDefinition` without `.WithLibrary(...)` | `TaskDefinition.WithLibrary(dynamicLib)` + `SendDllBlobAsync` upload |
| Instance lifetime | New instance per task | Cached per session, keyed by symbol + library blob id |
| Best for | Few, stable implementations | Many implementations, frequent iteration |
