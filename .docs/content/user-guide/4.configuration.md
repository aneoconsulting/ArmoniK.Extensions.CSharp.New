# Client Configuration

`Properties` (from `ArmoniK.Extensions.CSharp.Common`) reads its settings from a standard .NET `IConfiguration` (typically built from `appsettings.json` plus environment variables) and is passed to `ArmoniKClient`'s constructor:

```csharp
var configuration = new ConfigurationBuilder()
                    .AddJsonFile("appsettings.json", optional: false)
                    .AddEnvironmentVariables()
                    .Build();

var properties = new Properties(configuration);
var client      = new ArmoniKClient(properties, loggerFactory);
```

## `Grpc` section

```json
{
  "Grpc": {
    "EndPoint": "http://localhost:5001",
    "SSLValidation": "disable",
    "CaCert": "",
    "ClientCert": "",
    "ClientKey": "",
    "ClientP12": "",
    "EndpointNameOverride": "",
    "RetryInitialBackoff": "00:00:01",
    "RetryBackoffMultiplier": 2.0,
    "RetryMaxBackoff": "00:00:30"
  }
}
```

- **`EndPoint`** — the control plane's URL. Required.
- **`SSLValidation`** — set to `"disable"` for local/dev clusters without a trusted certificate chain.
- **`CaCert`** / **`ClientCert`** / **`ClientKey`** / **`ClientP12`** — mTLS material, when your cluster requires client certificates.
- **`EndpointNameOverride`** — overrides the SNI/authority name used for TLS validation, useful when connecting through a proxy or port-forward.
- **`RetryInitialBackoff`** / **`RetryBackoffMultiplier`** / **`RetryMaxBackoff`** — control the exponential backoff used when the underlying gRPC channel pool retries a call.

`ClientServiceConnector.ControlPlaneConnectionPool` uses these to build a pooled `ObjectPool<ChannelBase>`; unhealthy channels (`TransientFailure`/`Shutdown`) are automatically evicted and replaced.

## `ApplicationConfig` section

```json
{
  "ApplicationConfig": {
    "ParallelismLimit": 20
  }
}
```

- **`ParallelismLimit`** — caps concurrent in-flight gRPC calls made through the client's channel pool.

## Submission and callback tuning

These are read from `Properties` and control the background submission and callback-polling loops described in [Submitting Tasks](./2.submitting-tasks.md):

| Property | Default | Effect |
|---|---|---|
| `Properties.TaskSubmissionBatchSize` | `1000` | Max number of tasks grouped into one submission call |
| `Properties.TaskSubmissionBatchWindow` | `5s` | Max time a partial batch waits before being flushed anyway |
| `Properties.CallbackPollingInterval` | `5s` | How often the session's background poller checks blob status for registered `ICallback`s |

Raise the batch size/window for high-throughput bulk submission where a few seconds of extra latency per task is acceptable; lower them (or the polling interval) when individual tasks need to be picked up and submitted or reported on as quickly as possible.
